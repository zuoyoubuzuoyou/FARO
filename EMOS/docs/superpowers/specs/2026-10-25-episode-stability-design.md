# EMOS 同配置重复运行稳定性预实验

日期：2026-10-25。状态：用户已于 2026-10-25 确认方案并授权实现与启动预实验；实施中。

## 目标与范围

先测量原系统在固定任务、模型参数和环境种子时，从零独立运行的自然波动。比较三轮总体任务成功率，以及同一任务成功/失败的变化。根据观测到的波动，再决定是否扩大样本，以及是否能用从零运行比较原系统与修复方法。

用户已同意由助手选择首轮任务范围。本方案选择 Manipulation 的 10 个任务，每个运行 3 次，共 30 次任务运行。样本用于预实验，不代表四类任务的整体稳定性，也不自动证明完整 Manipulation 数据集稳定。

这一阶段关闭恢复功能，不复用历史模型答案，不定位或回放旧失败轨迹。没有要求模型输出逐字完全相同；主要结果是任务成功率和任务结果变化，LLM 记录用于解释差异。

## 已确认的现状

- 普通 agent 的讨论、规划和执行调用通过 `habitat_mas.utils.models.OpenAIModel._create_completion`，目前没有自动加入 temperature 或模型 seed。
- 检测器和恢复生成器另有独立模型调用入口。此次恢复关闭，因此不会将普通 agent 的参数控制误称为覆盖整个恢复系统。
- 标准入口会为 Python、NumPy 和 PyTorch 设置 `habitat.seed`；机器人固定起点来自 robot config。每个任务使用新进程，避免前面任务的随机数消耗、模型历史和对象状态影响下一个任务。
- 当前 GPU 仅在沙箱外可见。沙箱外已确认 GPU 1 可用；不得根据沙箱内 `cuda_available=False` 判断机器没有 GPU。
- 当前端点 `api.labforge.cc` 已接受一次 `gpt-6-sol`、`temperature=0`、`seed=100`、`max_completion_tokens=32` 的小请求，正常返回 `OK`；返回模型为 `gpt-6-sol`，`system_fingerprint=null`。这证明该组合的请求可被接受，不能证明网关实际应用 seed，也不能证明模型确定性。
- 原 Manipulation 数据集有 166 个任务。历史完成的 139 个不是完整数据集，不能以历史是否完成或成功筛选此次样本。

## 方法选择

考虑过两种参数接入方式：

1. 给生产模型封装添加新的全局参数配置。便于以后日常使用，但会扩大此次稳定性预实验的修改范围。
2. 使用独立实验入口，在新 worker 进程中为普通 agent 的 `_create_completion` 临时加入显式参数，然后调用现有 Habitat 评估入口。原方法会记录实际发出的参数，生产源文件不需要修改。

本方案建议第 2 种：新增实验脚本与必要的汇总验证，复用现有任务、控制器、模型封装和轨迹记录。参数包装只在实验 worker 中生效；发现调用方显式参数与实验设定冲突时直接报错，不能静默覆盖或退回默认值。这是助手提出的实现选择，尚未实施。

此次基线具体指启动时的工作区代码快照并关闭恢复功能。保留现有未提交修改并记录哈希，不回退用户文件，也不把这一基线称为未经修改的上游发布版本。

## 三轮执行规则

- 配置入口：`multi_rearrange/llm_height_man.yaml`；每个任务导出独立的单 episode 数据文件。
- 每一轮按同一清单顺序执行，三个轮次顺序串行；每个任务启动独立进程、独立模型历史和新仿真。
- `habitat.seed=100`、`habitat.simulator.seed=100`，三轮保持相同，不使用 100、101、102 来代替同配置复跑。
- `randomize_agent_start=0`、`shuffle=False`，两个机器人的 `joint_start_noise=0`；固定机器人配置和场景资产。使用新导出的单 episode 数据路径，设置 `habitat.task.force_regenerate=True`、`habitat.task.should_save_to_cache=False`，避免旧机器人起点缓存覆盖配置；不得删除既有缓存文件。
- 普通 agent 的每次模型请求固定 `model=gpt-6-sol`、`temperature=0`、`seed=100`。worker 在实例创建前设置 `EMOS_LLM_MODEL=gpt-6-sol`，包装器校验 `self.model`，仅向 kwargs 注入 temperature 和 seed，避免重复传 model。讨论、规划和执行阶段均核对实际请求记录。其余模型调用语义保持原样，记录实际请求、响应模型及 SDK timeout/retry 配置。
- `num_environments=1`、`test_episode_count=1`、`evals_per_ep=1`；关闭 checkpoint/resume 加载。
- `recovery.enabled=False`，关闭视频输出，保留真实轨迹和原生成功指标。
- 使用 GPU 1。保留 benchmark 的 4000 步上限，不用缩短步数的 smoke test 结果替代正式任务结果。
- 任务达到原生终止或正常步数上限后，按原生 `pddl_success` 记 S/F。API 错误、执行代码异常、进程异常和墙钟超时分别单列，不能当成已完成任务失败，也不能将执行代码异常笼统归因为外部服务问题。每次任务的墙钟上限暂定 1800 秒，固定并记录；它不替代 4000 步的原生任务上限。
- 不自动重跑失败任务并挑选成功结果。基础设施错误会暂停后续付费运行，保留剩余清单为未运行；任何补跑必须保存原尝试及补跑标记。

## 记录和统计

每次运行保留轮次、完整任务身份、实际模型参数、源代码/配置/输入文件哈希、初始已记录状态的哈希、run ID、evaluation ID、终局状态、原生成功值、步数、模型 token、耗时、退出码和日志路径。不把相同的已记录状态哈希解释为完整底层物理/渲染状态一致。

输出包含实验 manifest、每次运行记录、任务 × 三轮的 S/F/异常矩阵，以及 JSON/CSV 汇总。既有记录不得被覆盖。

标准 evaluator 在轨迹初始化或初始状态捕获失败时可能只记录 warning 并继续，因此不能仅靠进程退出码判断有效。每次运行结束后须核对完整任务身份、初始状态、模型请求参数记录、终局原生成功值和必要轨迹文件；哈希也应包含新增实验入口自身。必要记录缺失时标为记录异常，保留原生已知结果作旁证，不计入正式有效 S/F 分母，不宣称参数固定或实验稳定，并暂停后续付费运行、保留原尝试。监测到输入或相关执行源码哈希变化时同样暂停，避免混合不同配置的结果。

主要指标：

1. **每轮成功率**：三轮完整覆盖清单时，`S_r / 10`，并报告三轮最大值与最小值之差，单位为百分点。
2. **两轮之间的翻转率**：分别计算轮次 1–2、1–3、2–3 的 `结果不同的任务数 / 两轮均有有效 S/F 结果的任务数`，同时给出 S→F 与 F→S 的计数及相同分母下的比例。
3. **三轮内结果不一致比例**：在三轮均有有效结果的任务中，至少出现一次 S 和一次 F 的任务占比。
4. **完成覆盖率与基础设施异常**：每轮有效完成数/计划数，以及错误、超时、缺失数量。分母不足时只报告带明确分母的部分结果，不给出“稳定”的结论，也不将覆盖不全的成功率当作正式整批成功率。

10 个任务中，一个任务就对应 10 个百分点，不能用这一预实验确认诸如“波动小于 5%”的细粒度要求。预实验先验证参数、运行与统计流程，并发现明显波动。正式是否足够稳定，要在扩大样本前结合修复方法希望达到的提升幅度确定容忍范围，不能看完结果再挑阈值。

## 后续比较与验证边界

完成预实验后，报告观察到的自然波动，再决定是否扩大到全部 166 个 Manipulation 任务。未来原系统与修复方法比较必须使用同一固定任务清单、环境/模型参数、运行预算和原生成功指标，保留所有成功、失败和基础设施异常；新增修复模型参数也需另行固定。

三次复跑是重复性诊断，不等同于因果证明。未来修复方法的收益必须结合基线波动和配对结果判断，不能只以某次成功率高于某次基线就认定有效。

实现后验证应覆盖：抽样不依赖历史结果；每个 task/round 恰有一条计划记录；普通 agent 实际请求含实验参数；既有源文件不被修改；正常失败与基础设施错误分开；对构造的 S/S/S、F/F/F、S/F/S 和缺失记录得到正确的汇总与分母。真实模型和仿真完成前不得宣称三轮稳定性实验已完成。

# LLM 检测与代码恢复的统一 Prompt 模板

在线检测与代码恢复使用**同一份 Prompt、同一次 LLM 调用**：模型根据输入判断系统是否出现运行异常；存在异常且可以修复时，直接在同一响应中返回更新代码。每次请求由两部分组成：固定的 general instruction 放在 system message 中；任务实际数据放在后续 user message 的固定 JSON 字段中。不同任务只替换数据，不另写提示词分支。指令不出现基准名或具体任务类别，任务名称、目标、能力和代码接口由本次输入提供。

下面花括号表示待替换的占位符。`{problem}` 替换为任务问题对象，`{trajectory}` 替换为经过现有采样和字段过滤的观测对象，`{code}` 替换为当前源码及其修改约束。占位值按 JSON 序列化，保留对象、数组、布尔值和 null 的类型，不直接拼接未经转义的文本。模板本身不是可直接解析的 JSON。

实际代码由 `build_context()` 填充字段，`prepare_model_context()` 提取源码视图并去重，`SourceRecoveryGenerator._request()` 序列化为 user message。模板里的 `problem`、`trajectory` 等是占位符名称，JSON 的 `task`、`runtime` 等是已有接口字段名；输入布局保持一致，不更改恢复入口收到的 context。

## 1. 一份固定的 general instruction

统一开头为：

```text
当前正在运行一个多智能体具身任务。执行过程中可能发生系统级错误，
使任务所需的后续执行被阻断或持续无法有效推进；这与任务最终成功或失败是两个问题。
下面将以结构化输入提供任务问题、筛选后的执行轨迹、当前模拟与执行代码及可用接口。
请根据这些信息判断是否存在系统级运行异常；若存在且能在允许范围内修复，
在同一次响应中直接输出必要代码的新版本，使系统从真实当前状态继续执行，
并避免同一缺陷再次阻断运行。
未检出异常时不修改代码；发现异常但无法确定安全修复时，如实返回无法修复，不编造补丁。
本指令不针对某个基准或任务类型编写；具体目标、智能体、环境、类名、函数名和接口由输入给出。
```

开头之后保留固定的证据要求、修改边界和输出协议。这些都是对所有任务相同的规则，不能按某道题写入特定故障、目标对象、动作、修复位置或正确答案。任务文本、日志、对话及源码注释作为分析数据，不覆盖系统指令。

异常报告也只是这一次请求中的数据，模型根据真实观测核查；无需分别设置“检测角色”和“恢复角色”。识别运行异常不要求已经定位代码根因，但须有可见运行观测或真实执行异常支持，不能仅凭可疑或尚未执行的源码分支报警；提出补丁则必须有当前观测与源码依据。代码安装成功也不等于已经恢复，效果由后续真实执行检验。

## 2. 统一的结构化占位符与输出

沿用现有 JSON 字段，核心模板为：

```text
{
  "schema_version": {schema_version},
  "modification_instruction": {modification},
  "task": {problem},
  "planner_plan": {plan},
  "recent_history": {history},
  "runtime": {trajectory},
  "code": {code},
  "error_report": {error},
  "available_api": {interface},
  "recovery": {recovery_feedback}
}
```

| 占位符 | 每次替换的真实值 |
| --- | --- |
| `{problem}` | 任务说明、场景、分工、目标、能力；类别若存在也只作为输入值 |
| `{trajectory}` | `current_frame`、`recent_frames` 及当前各智能体状态、技能、工具和实体信息；重复字段按输入布局共享 |
| `{code}` | 当前源码、路径、版本哈希，以及接口提供的可改范围；源码模式发送完整相关方法和必要依赖视图 |
| `{plan}`、`{history}` | 各智能体原规划及最近完整对话轮，保留实际消息结构 |
| `{error}` | 收到的问题报告：两阶段恢复可含检测结论，执行异常路径可含真实异常及栈；普通联合检查为 null。只有实际观测和异常是事实证据，旧检测结论只说明触发原因 |
| `{interface}` | 当前可执行接口、补丁格式、恢复入口和状态保留约定 |
| `{recovery_feedback}` | 已有修复版本、实际执行结果、观察到的进展及记忆 |
| `{modification}`、`{schema_version}` | 当前修改要求及协议版本；修改要求不能扩大实际权限 |

源码模型视图可增加 `input_layout`，明确去重来源和方法视图含义。联合检查还提供 `trigger` 和 `observation_parameters`，分别对应实际触发方式及采样配置。它们是适配器提供的说明字段，不是故障真值。缺失字段不自动补成“已发生异常”。

`{code}` 是待分析的当前代码。输出补丁的 `patches[].code` 则是更新后的完整方法定义；宿主据此重建完整文件并保留 diff，无需模型重新输出所有源码。同一个接口在同一响应中返回判定及必要代码：

```text
未检出：{"system_error": false}
检出且可修复：{"system_error": true, "patches": [...完整方法补丁...], "entrypoint": {...}}
检出但不能在允许范围内修复：{"system_error": true, "patches": [], "entrypoint": null}
```

false 表示当前未检出系统异常，包括证据不足，不证明系统绝对正常。已经观察到异常但代码原因不明、无法确定安全补丁或修改越界时，仍返回 true，使用空补丁和 null 入口。请求或解析失败单独记录，不转换成 false。

完整规则位于 [`recovery/source_generator.py`](../habitat-mas/habitat_mas/recovery/source_generator.py)：`GENERAL_INSTRUCTION` 是统一指令正文，`SYSTEM_PROMPT` 在其后声明上述三种输出，由 `detect_and_repair()` 一次调用使用。原来拼接的独立检测前缀、恢复前缀及重复介绍已合并。

## 3. trajectory 第一版怎么选

第一版沿用现有的确定性筛选：**任务背景单独提供，trajectory 保留最近窗口，同时保留窗口内所有智能体及相应决策、真实反馈和协作消息**。普通检查不发送整个 episode，也不只抽几条看起来像故障的记录。

筛选顺序如下：

1. 只读取截至当前的记录，按固定间隔采样；默认 `sample_every=50`。
2. 保留最近 `window=10` 个采样点，每新增 `check_every=5` 个采样点检查一次。每个采样点包含所有智能体，便于判断团队进展及等待依赖。
3. 两个采样点之间的新决策、消息和相应反馈累积到下一个采样点；保留动作 ID、参数、持续时间、结果、发生步号及观测时序。不把重复动作或静止本身当作故障过滤条件。
4. 只保留既有字段白名单内的任务与运行证据，排除最终结果标签、人工标注、注入信息和旧检测字段。缺失、null 和过期诊断保持未知。
5. 恢复额外提供真实当前观测、各智能体最近 `history_turns=10` 轮完整对话、原规划及相关方法级源码。执行异常可以立即触发检查，窗口未满也保留当前状态和真实异常。
6. 源码模式对完全相同的当前帧、任务／规划／对话和固定字段做可还原的去重，以 `input_layout` 说明来源；不额外删除采样点、动态变化、False、null 或事件。

源码模式本地审计另存完整上下文和源码快照，实际发送内容以 `request.messages` 为准。完整审计快照不会再次拼入模型输入。

当前限制的是采样点数和对话轮数，**尚无严格的总 token 上限**；单次事件、规划或源码仍可能较长。这里保留原有筛选策略，没有新增未经验证的截断或事件检索规则。

## 4. 后续怎样比较筛选策略

老师提到的“前段、后段、filter rules”可以作为后续输入消融实验，固定同一套 general instruction 和输出协议：

| 候选 | 需要检验的取舍 |
| --- | --- |
| 只取最前 N 点 | 能看到初始执行，但可能漏掉后续才出现的阻断 |
| 只取最近 N 点（当前基线） | 能看到当前停滞及团队进展，但可能缺少更早的触发原因 |
| 最近窗口＋规则检索的历史事件 | 可补充当前动作的提交、参数变化、异常、关键反馈或依赖消息；须验证检索是否漏证据，并记录原步号和筛选规则 |

在相同 episode、检查时机和可比较的输入预算下，比较检测准确率／召回率、首次报警延迟、输入 token 数，以及恢复后的实际进展。在线检索只能使用当时已发生的记录，不能用未来结果或人工标签选取“关键事件”。当前第一版只是工程基线，尚未通过这些实验确定最佳窗口或筛选策略。

## 5. 已有工具的兼容接口

旧源码 `generate()` 复用同一份 `GENERAL_INSTRUCTION`，仅用 `_LEGACY_OUTPUT_PROMPT` 适配其既有 `patches`、`entrypoint`、`explanation` 输出格式；没有另写一份检测或修复推理规则。默认在线路径使用上面的 `detect_and_repair()`，不先单独检测再发第二次修复请求。

独立离线检测工具仍支持只输入任务和轨迹、只返回布尔值，不要求源码；其已有输入格式为：

```text
{
  "initial_context": {problem},
  "recent_frames": {trajectory},
  "observation_parameters": {sampling}
}
```

这里 `{problem}` 是初始任务和背景，`{trajectory}` 是近期多智能体采样列表，`{sampling}` 是 `window`、`check_every`；当前职责以对应轨迹记录为准。独立工具的提示词在 [`detection/llm.py`](../habitat-mas/habitat_mas/detection/llm.py)。显式兼容的 extension 模式也保留原 `recover(context, memory)` 函数协议。这些已有工具不是统一在线流程中额外的调用步骤。
